## What works
- **Eliminating intermediate stack allocations via direct memory fetches:** Replacing large read-only array allocations with direct memory fetches or localized scalars prevents register spilling and reduces L1 memory traffic (`strip-internal-array-allocations` ~11.9%, `compound-near-miss-optimizations` ~6.2%).
- **Exploiting mathematical symmetry and direct inlining:** Bypassing generalized arrays/matrices to inline convolutions algebraically directly inside the macro eliminates function call overhead and drastically reduces the instruction count (`inline-symmetric-convolutions` ~11.7%, `decompose-anisotropic-to-isotropic-base-and-correction` ~1.7%, `inline-isotropic-convolutions` ~1.2%).
- **Nontemporal (streaming) stores for write-once buffers:** Utilizing nontemporal stores for large buffers that aren't immediately reread (e.g., HF details, final PDE output) avoids cache write-allocate pollution (`nontemporal-hf-writes-in-decomposition` ~7.3%, `nontemporal-output-stores` ~1.3%).
- **Outer-loop unswitching for heavy mathematical blocks:** Unswitching is highly effective when evaluating binary conditions outside the pixel loop allows the inner loop to skip expensive `sqrtf`, divisions, or `expf` operations (`outer-loop-unswitch-isotropic-math` ~6.4%, `outer-unswitch-zero-speed-order-pairs` ~2.8%).
- **Shared `always_inline` hot-path helpers plus small specialized wrappers:** Factor the heavy pixel/row body into inline functions, but keep `DT_OMP_FOR()` in small per-specialization wrapper functions so the outlined OpenMP worker still sees literal flags. This preserves compile-time dead-branch elimination without bringing back giant macro bodies.
- **Refactoring macros by splitting outer specialization from inner shared work:** When replacing an unswitched macro, move only the shared inner body into `always_inline` helpers. Keep the specialization boundary explicit with one wrapper function per valid flag combination, or an X-macro-generated list of such wrappers. If the old code specialized on booleans before entering the parallel loop, the new code must preserve that structure.
- **Function-level pass skipping:** Testing for negligible scale weights before processing safely eliminates entire image passes and memory allocations without inner-loop disruption (`skip-hf-decomposition-for-negligible-scales` ~5.0%, `skip-pde-negligible-norm` ~2.0%).
- **Pre-combining parameters algebraically:** Pre-summing matched variables (like LF+HF stencil sums) outside the loop when parameters are identical effectively halves convolution evaluations (`precombine-stencil-sums-for-matched-orders` ~3.0%).
- **Peeling spatial loops to eliminate boundary clamping:** Splitting loops into edge and center regions allows the hot center path to safely drop spatial `MAX`/`MIN` boundary checks (`peel-column-loop-to-eliminate-clamping` ~2.4%).
- **Absorbing scaling factors into loop-invariant constants:** Eliminating per-pixel multiplication by factoring the constants outside the main iteration loop directly reduces ALU pressure (`compute-cos2-sin2-directly` ~2.3%, `remove-0.5-scaling` ~1.5%).
- **Compounding related near-miss optimizations:** Combining structurally related optimizations that target the same bottleneck (like stack array elimination) can unlock significant gains where they failed individually (`compound-near-miss-optimizations` ~6.2%).
## What to avoid
- **Leaving stale comments after refactoring:** When code is changed or removed, all comments that described the old behaviour must be updated or deleted. Reviewers flagged stale comments left behind after gradient elimination (commit 3a28481). Always re-read surrounding comments after any change.
- **Large macros instead of structured specialization helpers:** The DIFFUSE_ROW_LOOP macro (commit 662ff7c) was flagged as a maintainability problem. Avoid giant body macros, but do not replace them with one generic helper if the old macro encoded compile-time specialization. Prefer shared inline helpers plus small specialized wrapper functions or an X-macro-generated dispatch layer.
- **Unswitched code duplication without factoring:** DIFFUSE_PIXEL_BODY (commit bede39b) was flagged for creating unmaintainable repeated code. Repeated snippets from unswitching MUST be factored out into `always_inline` functions.
- **Moving `DT_OMP_FOR()` into a generic helper that takes hot-path flags as parameters:** Treat this as unsafe by default. `always_inline` is not enough once OpenMP outlines the parallel worker. If `GRAD_ISOTROPIC`, `LAPL_ISOTROPIC`, zero-order flags, or matched-order flags become ordinary parameters at the function that contains `DT_OMP_FOR()`, assume the worker will lose compile-time specialization and reject the change.
- **Collapsing many unswitched entry paths into one runtime-dispatched parallel loop:** If the old code had distinct outer dispatch arms for combinations like isotropic/anisotropic, zero/nonzero, or matched/unmatched orders, do not merge them into one function that branches internally around the OpenMP loop. Keep separate wrapper entry points so those flags remain constants at the parallel-loop boundary.
- **Altering the `expf` boundary or manually scalarizing SIMD state:** Moving or inlining `dt_vector_exp`, or explicitly unrolling/scalarizing core accumulation arrays catastrophically breaks compiler vectorization and scheduling (`inline-expf-evaluation-anisotropy` -170.9%, `inline-scalar-expf` -114.4%, `explicit-scalarization-of-accumulation-arrays` -111.8%).
- **Dynamic inner-loop branches or condition checking:** Skipping operations (`if (speed == 0)`), evaluating opacity, or copying matched results based on per-pixel conditionals severely degrades SIMD efficiency (`defer-symmetric-combinations` -91.7%, `copy-matched-anisotropy-c2` -83.7%, `skip-zero-speed-orders` -82.4%).
- **Fusing distinct iteration loops:** Merging multiple sequential `for_each_channel` passes or blur passes into a single massive loop heavily spikes register pressure, causing massive stack spilling (`pair-4-compute_convolution-calls` -48.7%, `fuse-variance-regularization` -8.2%).
- **Disrupting hardware prefetcher access patterns:** Removing linear row progression, altering row bound calculations, cache-blocking vertical strips, or adding software prefetch hints ruins L1/L2 memory throughput (`remove-dwt-interleave-rows` -30.1%, `unswitch-row-bounds-for-static-offsets` -26.7%, `cache-block-pde-column-strips` -12.4%).
- **Incorrect application of nontemporal/temporal stores:** Using streaming stores for LF/blur passes where data is consumed immediately in the next scale bypasses caches entirely and ruins performance (`nontemporal-lf-writes-in-decomposition` -68.8%). Conversely, reverting to temporal stores for intermediate PDE scale outputs also regresses performance (`temporal-stores-for-intermediate-pde-scales` -6.0%).
- **Outer-loop unswitching for lightweight savings:** Duplicating macro blocks to skip a single multiply, mask check, or redundant array bloats the instruction cache, negating the minor ALU savings (`outer-loop-unswitch-matched-anisotropy` -17.1%, `outer-unswitch-zero-lf-contribution` -15.4%, `outer-unswitch-zero-sharpness` -13.1%).
- **Micro-optimizing ALUs with explicit fast-math:** Replacing standard operations with manual algebra tweaks, `rsqrt`, explicit FMA chains, or inverse-magnitude multiplications generally outsmarts the compiler and regresses the code (`unify-direct-neighbor-sums-isotropic` -7.9%, `extract-inverse-c2` -4.4%, `explicit-fmaf-variance-chain` -2.2%, `rsqrt-anisotropic-magnitude` -0.8%).
- **Reordering, phasing, or interleaving memory loads:** Attempting to interleave LF/HF loads or reordering computation blocks (e.g., swapping sum and angle loops) disrupts the compiler's native scheduling (`phase-gradient-laplacian` -4.0%, `interleave-lf-hf-neighbor-loads` -3.5%).
- **Eliminating small overheads (allocations, setup, dead code):** Pooling buffers, hoisting scale parameters, or trimming unused matrix generators provides negligible speedup because setup time is invisible against the billion-pixel processing loops (`allocate-contiguous-hf-buffer-pool` -5.1%, `hoist-omp-parallel-across-scales` -2.7%).
- **Refactoring already optimized algebraic paths:** Further attempting to factor constants, fuse matched anisotropic tensors, or tweak the mathematical structure of the recently optimized paths yields zero or negative return (`fuse-matched-anisotropic-tensors` -7.1%, `factor-quarter-scaling-isotropic` -2.6%, `eliminate-sin-theta-sq-arrays` -0.5%).

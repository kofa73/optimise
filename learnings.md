## What works
- **Exploiting kernel/data symmetry to significantly reduce operation count:** Identifying mathematical symmetries and using algebraic identities to eliminate large fractions of work. inline-symmetric-convolutions pre-combined symmetric neighbor pixels and reduced 36 multiplications to 16 per channel (~11.7% improvement). Key: the reduction must be substantial (e.g., halving operations), not marginal.
- **Replacing intermediate arrays with scalar variables:** Removing small stack-allocated arrays in favor of direct inline scalar computation reduces memory traffic and register pressure. Confirmed twice: inline-symmetric-convolutions eliminated 9-element `kern_*` arrays (~11.7%), and strip-internal-array-allocations inlined `find_gradients` normalization arrays into native scalars (~11.9%). Both gave ~11-12% gains — this is the most reliable pattern observed.
- **Preserving identical floating-point evaluation order:** Both successful optimizations were careful to produce bit-identical results by not reordering multiply-accumulate sequences. This is a prerequisite, not an optimization itself.

## What to avoid
- **Changing floating-point evaluation order:** Pre-combining or rearranging multiply-accumulate operations — even when mathematically equivalent — changes rounding sequences and causes benchmark errors. fuse-paired-kernel-convolutions failed by combining `kern_first[k]*ABCD[0] + kern_second[k]*ABCD[1]` before convolution. skip-zero-speed-orders also caused benchmark errors by skipping computations entirely when coefficients were zero.
- **Micro-optimizations that save only 1-2 instructions:** simplify-b22-trace-identity replaced one addition with a trigonometric identity (`b22 = -2.0f * (1.0f + c2)` instead of `-2.0f * (a[0][0] + a[1][1])`). Despite being mathematically simpler, it caused obvious regression — likely because the compiler already optimizes this, and the change disrupted its optimization decisions.
- **Restructuring code without reducing algorithmic complexity:** rewrite-9-element-kernel-matrix-instantiation inlined kernel construction with algebraically reduced scalars. It regressed on this workload despite succeeding on different test data previously, suggesting the compiler's existing optimizations were already effective and the rewrite interfered with auto-vectorization or instruction scheduling.
- **Conditional branching to skip work:** Adding conditionals to skip zero-contribution computation causes benchmark errors (skip-zero-speed-orders) — even when checks are outside the pixel loop. The code path changes alter floating-point accumulation and break bit-exactness.
- **Over-merging loops:** Fusing fundamentally different computational stages causes register spilling, breaks auto-vectorization, or destroys cache locality.
- **Fast-math/precision reductions:** Lower-precision intrinsics or `#pragma GCC optimize("fast-math")` cause regression test failures due to strict numerical precision requirements.

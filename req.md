# Purpose and method
Aim: a configurable Python script that invokes shell commands, other scripts and LLM CLI interfaces to perform the configured optimisation task.
Solution: the script is a state machine, whose behaviour is described below.
Key constraint: scripted execution for ALL deterministic steps (exection, state management, file operations (except for the coding step), parsing/generation of deterministic input/output. LLM use restricted to generation, evaluation and implementation (coding) that deals with natural and programming languages. All calculations (statistics etc) MUST be done via python, avoiding ANY LLM 'mental maths'.

# Git repos
The optimisation process MUST use 2 separate git repos:
- one holding the to-be-optimised code base (we will call this the "target repo");
- one containing the optimisation script, its configuration and state, including the performance data, ideas, learnings (we will cause this the "script repo").
This separation ensures that:
- the state of the script can always be committed
- the target repo only accumulates successful attempts, reducing clutter when subsequently a pull/merge request is created (no files that do not belong to the code base, but to the state of the optimisation process; no commits that just record a failed attempt)
- the target repo can still be used to roll back the optimisation target to a known good state after a failure

# Notion: "idea"
- each idea is a markdown file
  - name: a *very* brief summary of the idea; may only contain [a-zA-Z0-9_\-]+; the extension MUST be .md. For example: `precompute-half_anisotropy-outside-loop.md`. The LLM MUST generate the name without extension. The script MUST ensure that if the name does not match the regex, any non-confirming characters are replaced with _ (underscore), and the script MUST ensure the extension is ".md" (if the LLM, by mistake, added an extension, the script MUST strip it and add ".md". For example, if the LLM proposed the file name "precompute half anisotropy outside loop, to improve gradient calculation speed.txt", it MUST be converted by the script to "precompute_half_anisotropy_outside_loop__to_improve_gradient_calculation_speed.md".
  - format:
    - one line title, suitable for a commit message header. Example: "remove 0.5f scaling from gradient/laplacian, absorb into half_anisotropy"
    - a short description, for extended info to be included in the commit. Example:
      Remove the 0.5f central-difference scaling factor from gradient and
      laplacian computation. The factor cancels in angle ratios (cos²θ, sin²θ,
      cosθsinθ) since they are computed as gx²/m², gy²/m², gx·gy/m². For the
      magnitude term, precompute half_anisotropy[k] = anisotropy[k] * 0.5f
      outside the pixel loop. This eliminates 4 float multiplies per pixel per
      channel from the hot path.
    - once done (see below for lifecycle), a last section: outcome: quality regression / performance regression / improvement / coding error. The LLM only generates the title, the description
- directory ideas/, inside that ideas/todo/ (one small markdown file per idea), ideas/done/ (one file per idea), ideas/coding/ (always at most 1 file), ideas/testing (always at most 1 file)
- lifecycle:
  - creation:
    - ideas are generated by LLM calls, based on
      - the optimisation instruction (see below)
      - the code to be optimised (specified in the instruction)
      - the learnings (summary of experiences gathered while executing previous ideas, see below)
    - each newly generated idea is written into a Markdown file in ideas/todo. 
    - when the LLM generates a new idea, we must make sure the new idea does not match one of the previously generated ideas. So, after generating, read all the files under ideas/ (no matter which directory), and compare the newly generated idea. If there is a match, discard, and generate again. If no new idea is found in 10 cycles, stop generating. This loop (10 attempts) MUST be driven by the Python script.     - as long as there are fewer than 5 ideas in ideas/todo, the script must repeatedly invoke the LLM to create new ideas
  - selection
    - this must only be done if ideas/coding currently contains no file (if there is a file, something is in progress; see 'coding' step below)
    - the script calls the LLM to choose one of the ideas in ideas/todo. The LLM must return the name of the file. QUESTION TO ANALYSIS MODEL: would it be better if the script loaded all files from ideas/todo, created content from the file name and the contents of the file for each, concatenating this all, and passing it to the model with a prompt like "each section contains the name of an idea and it description; select the idea that is most likely to improve performance of <optimisation target>, and return its name", or should the invoked agent read the files itself ("read the files in ideas/todo; select the idea that is most likely to improve performance of <optimisation target>, and return its filename)"?
    - the script moves the selected idea to ideas/coding
  - coding
    - the script invokes the LLM, telling it to implement the idea in ideas/coding (there will be a single *.md file; there may also be an errors.txt file, if the previous build failed, see below). The LLM must take the contents of errors.txt into account (in order to fix coding errors). The prompt should reflect this; in addition to the instructions (read from settings, see below), the following MUST also be passed to the LLM: "The previous build failed; its output is in ideas/coding/errors.txt. You MUST fix the errors".
    - restart after failure:
      - it may happen, that the session is abruptly interrupted, for whatever reason; when the script starts up, it must check if the git status of <optimisation target> is dirty; if yes, then the previous coding session was interrupted, the file may half-done or even completely broken. The <optimisation target> must be restored to the last committed state, so coding can start from a known good state. The file ideas/coding/errors.txt MUST be removed.
  - building:      
      - after coding, the script (and NOT the agent) must build the application, so it can be tested. If the build fails, the script must ensure the build output is recorded in ideas/coding/errors.txt (overwriting any previous  has to be passed to the agent, telling it to fix it. This may be repeated 5 times.
        - If, after the retries, the build still failed:
          - the idea file MUST be moved to ideas/done;
          - the script MUST append a new line: "outcome: coding error"
          - the <optimisation target> must be restored to the last committed state
          - then, the script's main loop must be restarted (creating new ideas, if needed, selecting one, coding)
        - If the build worked (with or without retries):
          - the idea file MUST be moved to ideas/testing
          - the main loop MUST move on to the "testing" phase
  - testing
    - quality regression test: the script must invoke the quality check script, which must return a success/failure indication. If a quality issue is found, the idea file must be moved to todo/done by the script, and the script must append a line: "outcome: quality regression". The script must use git to return <optimisation target> to the last committed state. Then, the main loop must begin again (creating, selecting, coding).
    - if the quality check passes, the script must invoke the performance check script, which must return a success/failure indication, including the performance gain / loss.

# Performance testing
- the performance test script is provided via settings, and is not in the scope of this specification (it will vary by task)
- the output of the performance test script will conform to the following: 1 or more lines of the format <label>=<value>, <label>=<value>, ... . Example: all of these are valid, and may be mixed in the same file:
    - user=0.561, cpu=5.372
    - user=0.123
    - user=.234, cpu=0.051, gpu=0.180
    - user=.234, gpu=0.180
    
  Lines from the same script will typically have the same format, but it is possible that lines differ. An optimisation script will always output the same format, for each run (same number of lines; line number _n_ will always have the same format between different invocations; lines _n_ and _m_ may have different formats. Example:
  - run _m_:
    ```text
    user=0.561, cpu=5.372
    user=0.123
    user=0.234, cpu=0.051, gpu=0.180
    user=0.234, gpu=0.180
    ```
  - run _n_:
    ```text
    user=0.551, cpu=5.372
    user=0.123
    user=0.234, cpu=0.051, gpu=0.180
    user=0.234, gpu=0.180
    ```
- the main script MUST persist the output of the performance test script under the directory perf-logs/. The name of the file must be derived from the name of the idea, by appending "-perf" BEFORE the extension. Example: if the idea file name was "precompute-half_anisotropy-outside-loop.md", the performance test script's output must be stored as `perf-logs/precompute-half_anisotropy-outside-loop-perf.md`.
- the format of files in perf-logs/: Markdown tables, with columns extracted from the performance logs (not all rows may have data for all columns). Using the performance script output from above, the set of columns is: `["user", "cpu", "gpu"]`. The table then has one row for each line of input, for example:
  ```markdown
  # Individual timings
  | user | cpu | gpu |
  | ---- | --- | --- |
  | 0.551 | 5.372 | |
  | 0.123 | | |
  | 0.234 | 0.051 | 0.180 |
  | 0.234 | | 0.180 |
  ```
  A second table presents the sums (empty cells are assumed to have the value 0):
  ```markdown
  # Totals
  | user | cpu | gpu |
  | ---- | --- | --- |
  | 1.142 | 5.423 | 0.360 |
  ```  
  A third table the averages (empty cells are excluded from computations - here, "user" is present in all 4 rows, so 4 numbers are averaged (0.551, 0.123, 0.234, 0.234); "cpu" is present in 2 rows (5.372 and 0.051 are averaged), "gpu" is present in 2 rows (0.180, 0.180))
  ```markdown
  # Averages
  | user | cpu | gpu |
  | ---- | --- | --- |
  | 0.286 | 2.712 | 0.180 |
  ```
  For all tables, the number of digits after the decimal point is the maximum of the number of digits after the decimal point taken from the initial input, with rounding upwards.
- baseline: initially, perf-logs/ will be empty (if the directory does not exist in the current working directory, the script MUST create it). If the directory is empty, it means we are starting the performance optimisation. The script MUST:
  - ensure the code has no uncommitted changes (untracked files are OK). If uncommitted changes are present, it MUST inform the user and stop immediately
  - ensure the code is on a feature branch (not on main/master etc); it MUST inform the user and stop, if that is not the case
  - build the code
  - run the performance test script (the quality test can be skipped, normally the code is tested for quality regressions in the CI pipeline, so the initial state can be assumed to be compliant)
  - save the formatted output of the performance test script as perf-logs/baseline-perf.md
  - and immediately copy it to (or save it again as) perf-logs/current-best-perf.md
  - immediately commit the new files with the message: "<prefix> established baseline"

# Settings
- optimisation target: one or more files, specified using path relative to the root of the "target repo". These are the files the LLM must focus on. Depending on the instructions, it may touch other files.
- instructions: a Markdown file, specified using the path relative to the "script repo" (it MUST reside in the under the root of the script repo, navigating upwards using ".." is not acceptable).
  The instructions MUST be passed to the LLM verbatim. They may be like "optimise performance of the algorithms implemented in <optimisation target>; you MUST not touch any other file", or "optimise performance of the algorithms implemented in <optimisation target>; you MAY change code in files used by the target IF AND ONLY IF no other code in the application uses it (the code that is outside the target is used EXCLUSIVELY by the target)" or similar (up to the user).
